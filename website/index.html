Tugport deploys your apps to servers you own.

It is one Rust binary that runs next to Docker. Push a commit and Tugport builds it, switches traffic once the new version is healthy and serves it over HTTPS, with logs, charts, backups and scoped API keys for your AI agents built in.

$ curl -fsSL https://tugport.com/install | sh
View the source

It runs on Linux with systemd, on x86_64 or arm64. The installer sets up Docker if it is missing and prints a one-time link for creating your account. Tugport is free and MIT licensed.

Deploys

A push becomes a release, and a broken release never gets traffic.

Connect GitHub, Forgejo, Gitea, GitLab or any Git server with a deploy key. Tugport builds every push with your Dockerfile, Railpack, Nixpacks or buildpacks on a warm BuildKit cache, starts the new version next to the old one, and moves traffic only after its health check passes.

  • Rolling back to any of the last few images takes one click.
  • In a monorepo, watch paths redeploy only the services whose folders changed.
  • The outcome goes back to the commit on GitHub or Forgejo, and to Telegram, email or a webhook if you want it there too.

Agents

AI agents get their own users, keys and limits.

An agent is a user without a password. Give it a role on the projects it needs, and Tugport hands you its key along with setup lines for Claude Code, Codex, the CLI and curl. The MCP endpoint, the CLI and the API all check the same permissions.

  • Roles go from viewer to deployer, operator and admin. Deleting things and reading secrets need separate grants that no role includes.
  • Keys can expire, can be limited to IP ranges, and show when and where they were last used.
  • Every action lands in the audit log with the person or agent and the key behind it.

Logs and charts

Logs and charts are built in for every server and service.

Follow the logs of every replica live, search them, and scroll back past restarts and redeploys. Each server's CPU, memory, disk, network and GPU use and each service's CPU, memory and network are charted from the last hour back to the last 30 days, without a metrics stack to run beside it.

  • Alerts for high CPU, memory or disk use, crash loops, out-of-memory kills, failed deploys, failed backups and offline servers go to Telegram, email or a webhook.
  • Secret values are masked in logs before anyone, or anything, reads them.

Servers

More servers join with one command, or Tugport creates them for you.

A new server joins an encrypted WireGuard network by running the command the panel shows. Replicas spread across servers, services find each other by name wherever they run, and when a server goes away, its services start on the others.

  • Connect a Hetzner or AWS account, and Tugport creates servers in any region and adds or removes them as a pool's load changes.
  • Replicas follow CPU or request rate, and a site nobody visits sleeps until the next request wakes it.
  • A service can be pinned to a server, a label or a region.

Databases

Databases come with backups, test restores and replicas.

Run Postgres, MySQL, MariaDB, MongoDB or Redis next to your apps, with generated credentials and a connection string that every service in the project can use. Back them up on a schedule to S3-compatible storage or a disk, and check a backup by restoring it into a throwaway copy.

  • Read replicas run on other servers or in other regions, with read-only connection strings and a promote button.
  • Volumes can be backed up and restored the same way.

Secrets

Secrets only reach the containers that use them.

Every environment value is stored encrypted, and the key that opens them is sealed to the server's TPM when it has one. The rest of the design assumes that one of your services will be compromised someday, and keeps that from becoming a problem for the others.

They live in memory inside the container.

Secrets are written to memory-only storage and loaded by Tugport's init, so they never show up in docker inspect, on disk or in image layers.

Projects can't reach each other.

Each project sits on a network of its own, so a service can't reach another project's databases, and no container can open connections into the encrypted network between your servers.

Dangerous switches need a grant.

Privileged mode, the Docker socket, host networking and bind mounts stay off unless an admin with the destroy grant turns them on.

Agents can write secrets without reading them.

Reading a value takes the secrets grant. Without it, an agent sees only names, and values are masked in its output.

Two-factor sign-in is built in.

People add a TOTP code to their password from the sidebar. Agents have no password at all, only keys that you can revoke instantly.

Nothing phones home.

Tugport sends no telemetry, and its own outbound requests never carry your environment values.

Migration

Moving from Easypanel or Coolify is one command.

The installer notices an existing Easypanel or Coolify and offers to move it. Tugport reads the old panel's state, shows you the plan, and brings over projects, domains, certificates, environment, volumes and deploy webhooks while your apps keep running.

  • Data stays where it is: databases and volumes keep their directories, so nothing is copied.
  • The old panel is only stopped at the end, and tugport migrate rollback starts it again.

One binary

Tugport is one binary, not a stack of services.

A typical self-hosted panel is a web app with a reverse proxy, a database, a cache, a queue, a metrics server and a log shipper next to it, and every one of them needs updates and can fail on its own. Tugport keeps the proxy, certificates, builds, logs and metrics in one Rust binary, stores its state in a single SQLite file, and lets Docker run your containers.

Updating it is a button in the panel, and the proxy keeps serving while the new version takes over. There is no app store, no one-click templates and no teams or organizations, on purpose.

Install

You can try it on a fresh server in a few minutes.

Any Linux server with systemd works, from a small cloud machine to the box under your desk. Tugport needs ports 80 and 443 for your sites and 8484 for the panel until you give the panel a domain of its own.

  1. Run the installer as root.

    It checks the download against its published checksum, installs Docker if needed and starts Tugport as a system service.

  2. Open the link it prints.

    Create the owner account there, then turn on two-factor sign-in from the sidebar.

  3. Connect a repository.

    Create a project, add an app from Git, point a domain at the server, and push.

$ curl -fsSL https://tugport.com/install | sh
